# AI Photo Coach 项目架构说明

本文档用于帮助自己和协作者快速理解项目整体结构，尤其是后端设计、数据流转和后续扩展方式。

## 1. 项目在做什么

AI Photo Coach 是一个面向移动端 H5 的 AI 摄影分析与半自动修图项目。

它的核心目标不是“给一段 AI 评价”，而是形成一条可扩展的完整链路：

1. 用户上传照片
2. 系统创建分析任务
3. 后端异步执行图像分析
4. 返回结构化点评结果
5. 前端展示评分、建议、标注
6. 用户可继续触发裁剪、曝光、白平衡等半自动处理

所以这个项目本质上不是单纯的“AI 调接口页面”，而是一个围绕图片分析任务构建的完整产品骨架。

## 2. 整体技术架构

当前项目采用单仓结构，主要分为 5 个部分：

- `apps/web`
  - Vue3 + Vite + Pinia
  - 负责移动端 H5 界面、上传、结果展示、历史记录
- `apps/api`
  - FastAPI 主服务
  - 负责接口、任务创建、数据读写、结果返回
- `apps/worker`
  - Celery Worker
  - 负责异步执行分析任务和未来的编辑任务
- `packages/contracts`
  - 前后端共享协议
  - 定义 `analysis_result`、`annotation`、`edit_action` 的结构
- `infra`
  - Docker Compose
  - 负责编排 PostgreSQL、Redis、MinIO、API、Worker

配套基础设施：

- PostgreSQL：存业务数据
- Redis：任务队列和状态缓存
- MinIO / S3：存原图、预览图、编辑结果图

## 3. 为什么要这样拆

这个拆法不是为了“看起来高级”，而是为了应对后续扩展。

如果把所有逻辑都写在前端和一个接口里，前期会快一点，但你一旦开始做：

- 异步分析
- 标注渲染
- 自动裁剪
- 曝光/白平衡处理
- 历史记录

代码会立刻失控。

所以项目从一开始就采用下面这条思路：

- 前端负责交互和展示
- API 负责组织流程
- Worker 负责耗时任务
- 数据库存状态
- 对象存储存图片

这条线是合理的，而且可以持续演进。

## 4. 后端架构总览

后端目前采用“接口层 + 服务层 + 任务层 + 数据层”的结构。

### 4.1 接口层

接口层位于 `apps/api/app/modules`。

当前主要模块：

- `images`
  - 上传图片
- `analysis`
  - 创建分析任务
  - 查询任务结果
  - 查询历史记录
  - 重试任务

这一层只负责：

- 接收请求
- 参数校验
- 权限和用户归属校验
- 调用服务或投递任务
- 返回结果

这一层不负责：

- 图像处理
- AI 模型调用
- OpenCV 计算

这样做的原因是，接口层必须保持薄，否则后续接口一多会很难维护。

### 4.2 服务层

服务层位于 `apps/api/app/services`。

现在已经按职责拆成：

- `storage`
  - MinIO / S3 上传下载
- `cv`
  - 图像特征提取
- `llm`
  - 基于图像和特征生成结构化点评
- `rules`
  - 根据规则生成可执行编辑动作
- `composer`
  - 合并各阶段结果，生成统一 `result_json`

这是后端最关键的一层。

为什么一定要拆成这几部分：

- `cv` 负责“事实”
  - 主体在哪里
  - 地平线在哪里
  - 哪些区域太亮或太暗
  - 图像亮度、对比度是多少
- `llm` 负责“解释”
  - 构图是否合理
  - 曝光问题怎么描述
  - 给用户什么建议更像人话
- `rules` 负责“动作”
  - 自动裁剪框怎么生成
  - 自动曝光参数怎么计算
  - 白平衡参数怎么产出
- `composer` 负责“统一出口”
  - 把这些零散结果整理成前端能稳定消费的结构

这个分层决定了后面是否容易扩展。

如果把这些逻辑混在一起，后面一定会返工。

### 4.3 任务层

任务层位于 `apps/api/app/tasks`，由 Celery 驱动。

当前核心任务是：

- `analyze_photo.py`

它的执行流程是：

1. 读取任务记录
2. 将状态改为 `RUNNING`
3. 从对象存储读取图片
4. 调用 `cv` 提取特征
5. 将特征写入 `analysis_features`
6. 调用 `llm` 生成点评和评分
7. 调用 `rules` 生成可执行编辑动作
8. 调用 `composer` 产出最终 `result_json`
9. 将结果写入 `analysis_results`
10. 将任务状态改为 `SUCCEEDED`

如果中途异常：

- 回滚事务
- 将任务改为 `FAILED`
- 记录 `error_code` 和 `error_message`

这条任务流的价值在于：

- 分析可以异步执行，不阻塞前端
- 以后可以把裁剪、修图也变成独立任务
- 前端只需要轮询任务状态，不需要等待长请求

### 4.4 数据层

数据层就是数据库模型和表结构，位于 `apps/api/app/models`。

当前核心表如下。

#### `users`

用于记录用户。

当前阶段只做最小实现，主要是为了给图片和任务挂归属关系。

#### `image_assets`

用于记录图片资源。

不仅保存原图，也为后续的预览图、编辑图做准备。

关键字段含义：

- `parent_image_id`
  - 用于建立“原图 -> 编辑图”的父子关系
- `asset_type`
  - 表示这张图是原图、缩略图、预览图还是编辑结果
- `object_key`
  - 对应 MinIO/S3 中的实际文件路径
- `exif_json`
  - 用于后续存拍摄参数

#### `analysis_tasks`

用于记录任务状态，是整个系统的调度中心。

关键字段含义：

- `task_type`
  - 表示任务类型，比如 `ANALYZE`
- `status`
  - `PENDING / RUNNING / SUCCEEDED / FAILED`
- `attempt_count`
  - 重试次数
- `model_name`
  - 当前任务使用的模型名称
- `prompt_version`
  - 当前任务对应的提示词版本

这张表很重要，因为所有异步能力都要围绕它构建。

#### `analysis_features`

这是这次架构升级里新增的关键表。

它用来保存 CV 阶段得到的原始特征和事实。

例如：

- 主体框
- 地平线
- 高光/暗部区域
- 亮度统计

这张表的意义非常大，因为它把“事实层”和“语言层”彻底分开了。

后续如果你做：

- 标注系统
- 自动裁剪
- 自动曝光

都应该优先使用 `analysis_features`，而不是去解析 AI 返回的文本。

#### `analysis_results`

这是用户最终看到的分析结果。

它保存 `result_json`，包含：

- `summary`
- `suggestions`
- `scores`
- `features_ref`
- `annotations`
- `edit_actions`

你可以把它理解成：

- `analysis_features` 是“机器事实”
- `analysis_results` 是“产品结果”

## 5. 一次分析任务的完整数据流

一张图片从上传到展示，大致经历下面这条链路：

### 第一步：上传图片

前端调用上传接口，把图片传给 API。

后端做两件事：

1. 把图片上传到 MinIO / S3
2. 在 `image_assets` 中记录图片元信息

这一步结束后，系统已经知道：

- 图片是谁上传的
- 图在哪里
- 图片大小和尺寸是多少

### 第二步：创建分析任务

前端创建分析任务。

后端在 `analysis_tasks` 中插入一条记录：

- `task_type = ANALYZE`
- `status = PENDING`

然后把任务投递给 Celery。

### 第三步：Worker 执行分析

Worker 拿到任务后开始工作：

1. 从对象存储下载图片
2. `cv_service` 提取特征
3. 把特征写入 `analysis_features`
4. `llm_service` 基于图片和特征生成建议
5. `rule_service` 生成裁剪/曝光等动作
6. `result_composer` 产出统一结果结构
7. 把结果写入 `analysis_results`

### 第四步：前端轮询结果

前端不断查询任务详情接口。

如果状态为：

- `PENDING`
  - 任务排队中
- `RUNNING`
  - 正在分析
- `SUCCEEDED`
  - 展示结果
- `FAILED`
  - 提示失败并允许重试

这样前端逻辑很简单，后端也有足够空间处理长任务。

## 6. 为什么后端要坚持“CV 事实 + LLM 解释”

这是这个项目成败的关键。

如果完全依赖大模型生成坐标和建议，会有三个问题：

1. 坐标不稳定
2. 难以复现
3. 无法直接执行自动裁剪和修图

所以正确做法是：

- CV 负责定位
- LLM 负责解释
- 规则引擎负责生成动作

例如：

- 主体框：CV 算
- 地平线：CV 算
- 高光暗部区域：CV 算
- “主体偏左，建议裁右侧 15%”：LLM 和规则共同产出
- 真正的裁剪参数：规则引擎计算

这条思路的好处是：

- 结果稳定
- 可解释
- 可复现
- 可执行

面试时也更有说服力。

## 7. 为什么需要统一协议

后端如果每次想到什么就返回什么，前端后面会非常痛苦。

所以项目现在开始统一三类协议：

### `analysis_result`

这是给前端展示的总结果。

它是主协议。

### `annotation`

这是标注协议。

目的不是“随便画个框”，而是告诉前端：

- 这是什么类型的标注
- 它来自哪里
- 用什么坐标系
- 关联哪条建议

### `edit_action`

这是编辑动作协议。

目的不是告诉用户“建议调亮一点”，而是给系统一个明确动作：

- 裁哪里
- 曝光参数多少
- 白平衡怎么调

有了这层协议，前端展示、Canvas 标注、后端 OpenCV 处理才能共用一套数据。

## 8. 当前架构的优点

当前项目已经有几个很好的基础：

- 单仓结构清晰
- 前后端职责分离
- 异步任务链路已建立
- 结果用 JSONB 保存，适合持续扩展
- 已经开始引入共享协议和中间事实层

这些都说明主方向是对的。

## 9. 当前架构还没做完的地方

虽然方向对，但还没有完全闭环的部分也很明确：

### 迁移体系还不完整

目前数据库仍然偏开发期模式，后续应引入 Alembic。

### `cv_service` 还是轻量 mock 版本

现在的特征提取还只是基础统计和规则生成，后续需要接更真实的检测逻辑。

### `llm_service` 还没接真实模型

当前仍是结构化 mock 逻辑，后续需要替换为真正的多模态模型适配。

### 编辑任务还没独立成完整链路

自动裁剪、自动曝光、白平衡目前只是动作规划，还没形成独立编辑任务和输出图。

## 10. 推荐后续迭代顺序

最合理的推进顺序如下：

1. 先把真实模型接入 `llm_service`
2. 引入 Alembic，固定数据库迁移流程
3. 增强 `cv_service`，补主体框和地平线检测
4. 前端接入 `scores` 和 `annotations`
5. 实现 `edit_jobs` 和编辑结果图产出

这个顺序的好处是：

- 不会推翻当前代码
- 每一步都能形成可见成果
- 每一期都能继续用于演示和面试

## 11. 一句话总结

这个项目的核心不是“调用一个 AI 接口”，而是构建一条稳定的图像分析流水线：

- 图片进入系统
- 产生机器事实
- 生成用户可理解建议
- 输出可执行动作
- 持续扩展为标注与半自动修图能力

如果你始终围绕这条主线迭代，项目会越来越像一个真正的产品，而不是一个演示 Demo。
